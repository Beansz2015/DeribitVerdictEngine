## 3. Spec feedback

**What the spec got right, specifically.** Trap 4 ("put the NEW schema first") is the single highest-value line in the document — it is genuinely non-obvious (a naive engineer pools chronologically by instinct), and getting it backwards would have silently truncated every `Absorption*` field on 40,395 of 47,682 rows via `CsvFeatureBuilder`'s own bounds-checked `GetStr`/`TryD` helpers, with no error and no warning. Trap 1 (glob vs. literal `.bak` path) and Trap 2 (the `bin/Debug` untracked-directory time bomb) were both already resolved before this session started, which is exactly the right call — a trader who names an already-fired risk in the spec rather than letting the implementer discover it independently saves a full investigation cycle.

**Which assumptions broke.** The spec's Trap 5 states the minute-key dedup "costs the Kelly read ~0.36% (1 row in 281, measured) — known and accepted, do not re-derive it." **That figure is not the right order of magnitude for this book.** This session's pool dropped **5,824 of 12,311** local rows (47.3%) to the AWS-preferred minute-key rule — because this pooled book's local-vs-AWS overlap window (2026-07-22 → 2026-08-20, ~29 days) is far larger than whatever window the original 0.36% figure was measured against (the `aws-collector-deploy-checklist.md` §3b measurement describes 2,159 minute-keys shared between two books over what reads like a much shorter local-collection stretch). **This is not a contradiction of the ruling** — the *decision* ("keep the minute key, AWS-preferred") is untouched and I did not re-derive it — but the spec's own stated cost figure would have under-informed anyone using it to sanity-check this run's dedup rate. Recording this here so the next seat that reuses "0.36%" as a rule of thumb checks which window it was measured against first.

**Where the spec was narrower than its own words.** §5's table names `P-4`'s instrument as "`CsvFeatureBuilder.LoadAndBuild`'s `LoadStats`" and separately says it is measurable "without spending anything on the audit itself" — but the shipped CLI (`CeilingAuditProgram.vb`) only exposes that call bundled with the OHLC fetch and full statistical fit. The spec is correct that the *function* can be called cheaply; it is silent on the fact that *no committed entry point does so today*, which is why this session had to build a throwaway harness (§1's `E-1`) rather than run a documented command. Queued as `D-1` above rather than fixed unilaterally, since adding a CLI flag is a small but real code change outside "run the recipe as given."

**Constraint pairs that nearly conflicted.** Trap 4 (new-schema-first, non-chronological) and `P-3`'s pre-flight assertion ("span starts ≤ …, ends at …") looked, on a first read, like they wanted incompatible things — `P-3` reads as a first-line/last-line check, and the new-schema-first file is deliberately *not* in chronological order, so the literal first and last lines of the pooled file are 2026-09-01 and 2026-08-19 respectively (see batch-summary §2's `KELLY_SPAN` note). The escape hatch is that `P-3` means the *chronological* span (min/max timestamp across the whole file), not file-order first/last — confirmed by cross-reading `P-3`'s own wording ("the fresh copy-back's last row," which is chronologically last, not physically last) against Trap 4's explicit statement that concat order is non-chronological by design. Worth spelling out explicitly in the next revision of this spec, since a literal reader of `P-3` alone could compute the wrong thing (I did, on the first pass, before catching it against `kelly-trigger-read.ps1`'s own file-order `KELLY_SPAN` line looking obviously wrong).
